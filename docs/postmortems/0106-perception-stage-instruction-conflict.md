# Perception Received Outcome-Adjudication Instructions

Artifact-Version: 1

## Executive summary

A typed-reference diagnostic on a complete action batch did not improve first-response acceptance. One response requested 25 checks, mostly about task success and judgment quality. Inspection found that perception inherited a system prompt requiring coverage of assigned actions and concrete outcome rulings, despite its narrower executable responsibility.

## Summary

Both arms accepted two of three responses, all of them completion-only. Neither requested-check response passed materialization, and necessary-check semantics remained unassessed. A dedicated perception system prompt aligns model instructions with the existing onset visibility and reaction contract. It does not change the world, skip a stage or mechanically suppress checks.

## Timeline

- A full-world step stopped during perception after action compilation recovered.
- A reference-contract repair aligned schema types, catalog uses and runtime identities.
- A six-call diagnostic retained the complete source scene and exposed outcome-oriented checks plus two nonexistent rating selections.
- Review of the exact system message found general outcome instructions in the perception bundle.
- A perception-specific system asset and real-entry regression separate observer visibility from action completion, while retaining the other role bundles.

## Root cause

The system asset was shared according to the broad Truth role rather than its phase responsibility. Its stage restriction coexisted with demands to cover assigned actions, adjudicate success and propose effects. The user's perception instruction and the runtime schema constrained output shape but did not remove that conflicting decision policy. Successful parsing or a completion-only response cannot establish that the intended stage semantics were preserved.

The onset caller also computed a specific observer/action workset for candidates lacking a direct perception basis, but passed only the complete action set and dependencies to perception. The model therefore received neither the scheduler's selected observer/source-action pairs nor an explicit distinction between assigned questions and established sensory access.

## Guardrails

The [stage responsibility contract](../specs/0101-align-onset-perception-responsibility.md) binds perception to a dedicated system asset. [Real perception-entry tests](../../src/engine/mechanics/__tests__/perception-references.test.ts) inspect the actual model request during initial, repair and continuation calls, and retain valid observer checks, complete input evidence and engine-owned randomness. The prompt manifest makes changes to other roles detectable.

The [perception work assignment](../specs/0102-preserve-perception-work-assignment.md) carries the scheduler's exact questions through the existing capability and context builder. Real engine-step regressions verify this handoff without replacing candidate discovery or inferring visibility from membership in the list.

## Remaining limitations

The instruction conflict is directly observable; its causal contribution to model failures and latency requires a fresh controlled comparison. Prompt tests do not certify semantic understanding. Fewer checks, completion-only responses and small-sample format acceptance do not prove correct perception, preserved gameplay or an action-to-feedback time below sixty seconds.
