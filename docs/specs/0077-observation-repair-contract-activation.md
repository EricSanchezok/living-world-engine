## Intent

Connect the existing [slot-local repair contract](0070-slot-local-repair-batching.md) to the prospective integrated gameplay candidate. The selected observation component currently omits the contract, so different observer feedback fragments into separate requests. The user's continuing optimization authorization covers this explicit candidate change and its offline verification.

## Contract

An explicit candidate option pins the observation batching child's existing physical-cardinality-slot-repair-v2 contract and tail-v1 repair placement. It requires the existing reversible shared-json-v2 codec. Preserve the twelve-slot ceiling, repair limit, model settings, full logical contexts, target identities, validation and every other role. Historical variants without the option keep their original configuration.

This changes model-visible physical request cardinality instructions, example policy and repair layout. It is a prospective experiment change, not an equivalence claim for prior model outcomes. It does not establish semantic correctness or real latency and cost savings. No paid trial or default workbench promotion is authorized by offline test success; existing budget and independent source-review gates remain in force.

## Plan

Reproduce fragmentation through the registered observation component in a real SimulationEngine step. Activate the existing contract in the integrated checkpoint candidate and record it in the candidate description. Do not introduce another scheduler or reduce action cardinality.

## Verification

Compare final truth, agent state, observations and transaction replay with the previous configuration. Verify the registry accepts the composition, other roles remain equal, and unshared contexts are rejected. Run coordinator isolation tests, final-candidate review tests and check:fast before committing. Candidate preparation must retain current-commit admission evidence and the budget gate.
